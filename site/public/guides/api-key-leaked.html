APIキー便

APIキーが漏れたときにやること｜GitHubに公開してしまったら

最初にするのは、履歴を消すことではありません。
キーを止めることです。

内容の確認日: 2026年11月5日

結論

  • すぐにキーを止めるか、入れ替えます。GitHubは、公開されたキーは数分で機械に見つかると書いています。
  • コミットを消しても、リポジトリを作り直しても足りません。キーは有効なままです。
  • 本番が止まって困らないなら、古いキーを先に止めます。困るなら、新しいキーへ切り替えてから止めます。
  • 止めたら、使われた形跡と請求を確かめます。
  • 履歴の書き換えは、そのあとで要るかどうかを考えます。不要な場合も多いと、GitHubは書いています。

止める順番

公式の文は、2つに分かれています。

  • 古いキーを先に止める:Anthropic、AWSの復旧の記事、OWASP、GitHubのチュートリアル
  • 新しいキーへ切り替えてから止める:Google Cloud、Gemini、Stripe

どちらかが間違いというより、何を恐れるかの違いです。
迷ったら、次で決めてください。

状況順番
権限が広いキー、管理者のキー先に止める
身に覚えのない動きが見える先に止める
本番で使っていないキー先に止める
権限が狭く、不審な動きがなく、止めると本番が止まる新しいキーへ切り替えてから、すぐ止める

AWSは、本番が止まるなら短い遅れは許されることがあるとしつつ、管理者のキーや不審な動きがある場合は遅らせてはいけないと書いています。
AWSのルートユーザーのキーなら、すぐに入れ替えます。

AWS

  1. IAMコンソールで、ユーザー → ユーザー名 → セキュリティ認証情報 → アクセスキーと進みます。
  2. アクション → 非アクティブ化を選びます。
    元に戻せます。削除は元に戻せないので、先にこちらです。
  3. CloudTrailのイベント履歴で、ルックアップ属性を「AWSアクセスキー」にして、キーのIDを入れます。
    見られるのは過去90日です。
  4. Cost Explorerで、漏れた日から今日までの費用をサービスとリージョンごとに見ます。

発行済みの一時的な認証情報は、キーを止めても残ります。ロールを使っていたら、IAMコンソールのロール → Revoke sessions → Revoke active sessionsで止めます。

AWSが隔離のポリシー（AWSCompromisedKeyQuarantine）を付けていたら、対応が終わるまで外さないでください。
早く外すと、AWSの救済措置の対象に影響することがあると書かれています。
相談はSupport Center → Create case → Account and billing → Securityです。

Google Cloud

  1. 認証情報のページで、キーの名前を押します。
  2. 「鍵をローテーションする」を押し、名前と制限を確かめて作ります。
    この操作はコンソールでだけできます。
  3. アプリを新しいキーに替えます。
  4. 新しいキーの詳細ページの「前のキー」で、「前のキーを削除」を押します。
    誤って消しても、30日以内なら戻せます。
  5. LoggingかSecurity Command Centerで、アクセスが想定どおりかを確かめます。

請求について、Googleは個別に審査するとしています。
返金を約束する文は見つかりませんでした。

Gemini API

  1. Google AI StudioのAPI Keysのページか、Cloudコンソールで新しいキーを作ります。
  2. 新しいキーでアプリを動かします。
  3. 確かめてから、古いキーを無効にするか削除します。
  4. Cloudコンソールで、請求のログとAPIの使用状況を確かめます。

漏れたと分かっているキーは、Googleが止めることがあります。
次のエラーが出たら、そのキーは使えません。新しいキーを作ってください。

Your API key was reported as leaked. Please use another API key.

身に覚えのない請求は、請求のサポートに連絡します。
使いすぎを防ぐには、AI StudioのSpendのページで月の上限を決められます。
ただし試験提供で、10分ほどの遅れの間は超えることがあります。

OpenAI

  1. APIキーのページで、新しいキーを作ります。
  2. アプリを新しいキーに替えて、動くことを確かめます。
  3. 古いキーを無効にします。
  4. Usageのページで使用量を確かめます。

OpenAIの開発者向けの文書にある、入れ替えの順番です。
漏れたときの手順そのものは、ヘルプセンターが読み取れず確かめられませんでした。
権限が広いキーなら、順番を入れ替えて先に無効にしてください。

広告

広告の枠

Anthropic

  1. APIキーのページで、キーの横の3つの点を押します。
  2. 「APIキーを削除」を選びます。
    Disableなら元に戻せますが、Deleteは戻せません。
  3. 同じページの「キーを作成」で、新しいキーを作ります。
  4. ログと使用状況を確かめます。

公開のGitHubリポジトリで見つかったキーは、Anthropicが自動で無効にしてメールで知らせると書いています。
動かなくなったら、これも疑ってください。

GitHubのトークン

  1. 右上のプロフィール画像 → Settings → Developer settingsと進みます。
  2. Personal access tokensのFine-grained tokensかTokens (classic)を選びます。
  3. 対象のトークンのDeleteを押します。
  4. Settingsの「Archives」にあるSecurity logで、過去90日の動きを確かめます。

公開のリポジトリやgistにプッシュされたGitHubのトークンは、GitHubが自動で取り消します。
取り消されたトークンは元に戻せないので、作り直してください。

Stripe

  1. ダッシュボードの開発者 → APIキーで、対象のキーを探します。
  2. 「...」→ キーをローテーション（Rotate key）を選びます。
  3. 有効期限を選びます。
    「今すぐ」を選ぶと古いキーは消えます。最長7日は両方を使えます。
  4. 新しいキーで動くことを確かめて、古いキーを消します。
  5. ワークベンチで、普段と違う使われ方がないかを確かめます。

Stripeは、ほかのキーもすべて入れ替え、不正な請求は早く返金するようにすすめています。
誰も見ていないと思っても、入れ替えるようにと書いています。

履歴を消すかどうか

GitHubの文書は、キーを止めたあとなら、履歴の書き換えは不要なことが多いと書いています（"often unnecessary if you've already revoked the credential"）。
時間がかかり、ほかの人の作業も壊すからです。

キーではなく、個人情報などを消したいときは別です。
書き換えても、次の場所には残ることがあります。

  • ほかの人のクローンとフォーク
  • GitHubのキャッシュされた画面
  • そのコミットを参照するプルリクエスト

古いクローンを持つ人がgit pullとgit pushをすると、消したものが戻ります。
GitHubのサポートが手伝うのは、キーの入れ替えでは防げないと判断した場合だけです。

それでも消すなら、GitHubの手順に沿って進めてください。
git-filter-repoの2.47以降を使います。
強制プッシュのあとは元に戻せません。

git-filter-repo --sensitive-data-removal --invert-paths --path PATH-TO-YOUR-FILE-WITH-SENSITIVE-DATA
git push --force --mirror origin

通知が来ないから大丈夫、ではありません

GitHubは公開のリポジトリを調べていますが、あなたに知らせるとは限りません。

  • 提携先の形式のキーが見つかると、GitHubは提供元へ知らせます。
    提供元が止めることもありますが（"may"）、必ずではありません。
  • その知らせは、リポジトリの管理者には届きません。
  • あなた宛ての通知は、Secret Protectionを有効にしたリポジトリで出ます。

プッシュの時点で止める機能も、キーの種類によって違います。
GitHubの表の抜粋です（2026年11月5日時点）。

キー提供元へ知らせるあなたに通知プッシュを止める
AWSのアクセスキー○○○
AnthropicのAPIキー○○○
GitHubのトークン○○○
GoogleのAPIキー○○×
GeminiのAPIキー×○×
OpenAIのAPIキー○○○

Stripeも、すべての漏えいを見つけられるとは保証していません。
AWSは、不審な動きが見つからないことは安全の証拠にならないと書いています。

止めないまま放置されるキーは多いようです。
GitGuardian（漏えいの検出サービスの会社）の2026年の報告では、2022年に有効と確認された認証情報の64%以上が、2026年1月の再確認でもまだ有効でした。

次に漏らさないために

  • .envを.gitignoreに入れます。その変更もコミットして、ほかの人も守られるようにします。
  • プライベートでも安全ではありません。GitHubは、プライベートのリポジトリでも暗号化していないキーをプッシュしないようにと書いています。
  • プッシュ保護を確かめます。Settings → Code security → Push protection for yourselfです。
    公開のリポジトリへのプッシュを止める機能で、既定で有効です。
    リポジトリ単位の保護は、リポジトリのSettings → Advanced SecurityのSecret Protectionから有効にします。
  • キーの権限を絞ります。漏れたときの被害が小さくなります。APIキーの渡し方に書きました。
  • 新しいキーをチャットで渡さないでください。同じことが起きます。
